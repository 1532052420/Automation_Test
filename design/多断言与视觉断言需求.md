## 一、产品视角

### 1.1 要解决什么

一个元素往往需要一次验证多项：「写新歌按钮」要同时确认 出现、文案正确、图标没被改坏。现状只能拆成多个步骤重复添加，执行多趟、报告分散；logo/icon 是图片，uiautomator 读不到内容，**根本没法断言**。

### 1.2 方案一句话

主断言 = 现有操作类型（**语义、UI、生成代码全部不变**）；主断言为断言类（断言存在/文本/消失）时，③栏出现「辅助断言」卡，可为本元素追加 0~N 条辅助校验，**与主断言打包成一个页面方法**，一次执行、全量出结果。

### 1.3 执行语义（已确认）

**全量执行**：主断言失败不停，辅助断言逐条继续；每个失败当场截图（视觉断言附 基线/实际/diff 三联图）；全部跑完后若存在失败，抛一条 AssertionError 汇总全部明细（序号/描述/期望/实际）。报告一次看全，不需要修一条跑一轮。

### 1.4 分期范围

| 分期 | 内容 | 说明 |
|---|---|---|
| **P1（本期）** | 辅助断言卡（文本=/存在/消失）+ 视觉基线对比 + 颜色断言 | 零新增依赖（cv2/numpy/skimage/PIL 已装） |
| P2 | 全屏基准对比、尺寸/位置断言、忽略区域编辑、跨分辨率归一化（等比缩放后比 SSIM） | 视基线对比上线后的反馈决定 |
| P3 | OCR 文本断言（切图里文字的内容校验） | 需新增 tesseract 系统依赖 |

### 1.5 兼容性承诺

- 旧用例（单断言步骤）零影响：无 `aux_asserts` 字段时生成代码与现在完全一致；
- 反解器 `_call_to_step` 保持兼容：老调用形态照常解析；
- 主断言为非断言类（点击/输入等）时辅助断言卡不出现，界面与现状无差（设计图 1）。

## 二、UI 视角（组件规范）

1. **辅助断言卡**：插在 ③栏「特殊操作」与「操作参数」之间；浅蓝底（#f5faff）+ 蓝描边（#b3d8ff）圆角卡，与「三件套去向」提示同语言；头部 = 名称 + `新增·P1` 绿 tag + 右侧一句「主断言失败也继续执行」。
2. **辅助行**：序号圆点（#409eff）+ 类型名 + 删除 ✕；参数区两列栅格，控件复用现有 input/select 规格（12px、#dcdfe6 描边、聚焦 #409eff）；视觉行独占整行的三联图预览条。
3. **视觉基线行**：阈值滑杆（0.80~1.00，默认 0.95，accent #409eff）+ 采集/更新基线按钮（未采集=主色按钮，已采集=描边按钮）+ 三联图三槽（基线/实际/diff，未采集为虚线空槽，通过=绿 PASS 徽章，失败=红底纹+FAIL 徽章）。
4. **空态**：卡内提示「还没有辅助断言 —— 下方选择类型添加」；非断言类主断言时整卡隐藏，原位置显示一行 💡 提示（设计图 1）。
5. **夜间模式**：全部走 `html.night` 变量覆盖（卡底 #202126、输入 #17181b、提示 #9ca3af），见设计图 6；不引入新色板。
6. **图标**：操作卡沿用现有 SVG 图标体系（原型中的 emoji 仅为示意，实施时用 `OP_GRID_ICONS` 现有条目；视觉/颜色新增图标按 icon-generator 规范出 24×24 SVG）。

## 三、开发视角（改动清单与实现要点）

### 3.1 数据结构

```python
step = {
  'type': 'assert_visible', 'element': 'webview', 'param': '',
  'aux_asserts': [                      # 新增；可为空/缺省=完全旧行为

    {'type': 'visual_baseline', 'threshold': 0.95},
    {'type': 'color_check', 'rgb': '46,107,230', 'tolerance': 20},
```

### 3.3 视觉断言实现要点

- 截图：`driver.get_screenshot_as_png()` → PIL 裁元素区域（复用 `save_element_image` 的区域换算，修复 DPR 隐患）；
- 比对：尺寸不一致 → 直接判「分辨率不匹配，请重新采集基线」；一致 → cv2 SSIM ≥ 阈值；
- 三联图：基线/实际/diff 横向拼接为一张 PNG，`allure.attach` 直挂（`popup_handler.py:162` 先例），平台 `allure_tweaks` 缩略图自动生效；
- 基线存储：`page_objects/app_ui/android/demoProject/elements/baselines/<元素文件名>/<元素名>.png`（进 git，随包分发）；
- 基线采集 API：定位器侧 `POST /api/element/baseline`（选中元素 → 实时截图裁剪 → 落盘 + 返回缩略图）。

### 3.4 风险与首版边界

分辨率/DPR：首版限单设备型号 + 比对前尺寸校验；横竖屏仅竖屏；跨分辨率归一化列 P2。

## 四、测试视角（验收矩阵）

### 4.1 功能用例（P1 范围，每类 正常+错误 双路径）

| 组 | 用例 | 预期 |
|---|---|---|
| 辅助-文本 | 文本=正确值 / 文本=错误值 | 通过 / 汇总报错含该条明细+截图 |
| 辅助-存在/消失 | 元素在 / 元素不在 | 双向验证（沿用 opcheck 口径） |
| 视觉基线 | 无基线首跑（自动建立）/ 相似度达标 / 低于阈值 / 尺寸不一致 | 建立并注明 / PASS / FAIL+三联图 / 「分辨率不匹配」不硬比 |
| 颜色 | RGB 在容差内 / 超容差 | PASS / FAIL+实际色值 |
| 全量语义 | 主断言失败+2 条辅助失败 | 3 条全部截图；1 条 AssertionError 汇总 3 条明细 |
| 兼容 | 旧单断言用例回归 | 生成代码与现状逐字节一致 |
| UI | 主断言非断言类时辅助卡隐藏 / 夜间主题 | 与设计图 1/6 一致 |

### 4.2 回归范围

元素定位器 15 种操作类型（opcheck 29 条用例包直接复用）+ 添加测试用例弹窗既有 56 条用例（《元素定位器添加测试用例-测试用例.xlsx》）中受 ③栏改动影响的部分。

### 4.3 验收标准

设计图 1~6 的布局、控件、文案、颜色逐项核对；生成代码预览与真实落盘文件一致；每条失败断言在 allure 中有独立截图证据。
