> 调研日期：2026-09-28 · 结论供《多断言与视觉断言需求.md》与原型 proto-multi-assert.html 引用

## 一、现状盘点（断言链路）

### 1.1 断言模型：一操作 = 一步骤 = 一断言

- 前端 `element_locator/static/index.js:31-45` `STEP_TYPES`：断言类 4 种（断言存在 / 断言文本 / 断言Toast / 断言消失），与操作类型共用「类型+参数」三元组（`currentStepObj`）。
- 一个元素想同时验证「存在 + 文本 + 外观」，目前只能**重复添加多个步骤**，生成多个独立页面方法；没有主/辅结构，也没有外观层面的校验。

### 1.2 生成与执行链路（改造涉及的环节）

| 环节 | 位置 | 说明 |
|---|---|---|
| 页面方法生成 | `element_locator/case_generator.py:128-218 page_method_code` | 每种断言一个方法：`assert_<el>` / `assert_<el>_text` / `assert_<el>_gone`；失败=AssertionError 或 TimeoutException |
| 用例行生成/反解 | `case_generator.py:221-269 / 429-463` | `_call_to_step` 按 `assert_` 前缀+后缀反解类型——**新增断言形态必须同步改这里** |
| 前端镜像 | `index.js pkgMethodBlock / previewLine`（新建用例包时前端直接组装三件套） | 与后端逐分支镜像，需同步 |
| 易漏点 | `web_platform/app_testing/codegen.py:26-38` | 平台「用例编排」直接复用 case_generator，且本地硬编码类型词表，需同步 |
| 执行与证据 | `cases/app_ui/conftest.py:136-219` | 失败→自动截图+证据视频+allure 附件（全自动，业务零侵入） |
| 断言原语 | `common/appium/appOperator.py:575-592 assert_true_with_shot` | 通过→成功截图挂 allure；失败→截图后抛 AssertionError。**多断言的现成叠加原语** |

### 1.3 可参照的先例：接口测试 media_check

`web_platform/api_testing/media_assertions.py`：`check_media(path, options)` 一次探测、逐项校验、**errors 累积汇总**返回 `(passed, actual, error)`；`evaluate()` 做字段适配。UI 侧 `web_platform/static/api_testing.js:358-430` 为该类型渲染专属多输入框行（留空=不检查）。由此验证了「新增一种断言类型」的标准改动面（8 处，见需求文档·开发章节）。

## 二、视觉断言技术选型（五种方式评估）

**诉求对齐**：要断言的对象是 **logo、icon、文案（切图型）、文本**。logo/icon 本质是图片——uiautomator 读不到内容，只能走截图比对；纯文本型文案用现有「断言文本」读控件 text 属性即可。选型按此分层：

| # | 方式 | 原理 | 覆盖对象 | 依赖 | 评估 | 分期 |
|---|---|---|---|---|---|---|
| 1 | **元素视觉基线对比**（visual_baseline） | 首次采集元素区域截图为基线 → 执行时裁剪同区域与基线比对（SSIM/像素差异）→ 相似度 ≥ 阈值判定 | **logo / icon / 切图文案**（外观是否被改、错位、加载失败） | cv2+numpy+skimage **已装**，PIL 已在用 | ✅ 核心。三联图（基线/实际/diff）挂 allure，平台 `allure_tweaks.py` 缩略图展示零改动 | **P1** |
| 2 | **颜色断言**（color_check） | 元素区域主色 RGB 与期望值比对（±容差） | 状态色场景：角标红点出现/消失、按钮禁用态变灰、主题色变更 | PIL（`get_element_rgb` 思路已有，`appOperator.py:407-420`） | ✅ 轻量可选。与基线不重复：适合「只关心颜色语义变化」的断言 | **P1**（可选类型） |
| 3 | 全屏基准对比（screen_baseline） | 整屏 golden 图 diff | 页面级改版回归 | 同 1 | ⚠️ 动态内容干扰大，需忽略区域编辑器，成本高 | P2 |
| 4 | 尺寸/位置断言（bounds_check） | 元素宽高/坐标与基线比 | 元素错位、挤压变形 | 无（bounds 现成） | ⚠️ 与基线对比重叠度高（错位本身导致 diff），独立价值有限 | P2 |
| 5 | OCR 文本断言（ocr_text） | 截图区域 OCR 出文字与期望比 | 切图型文案的文字内容 | **pytesseract/tesseract 未安装**，需新增系统级依赖 | ⚠️ 首版不做；基线对比已能发现切图文案变更（变更需人工看 diff 图确认性质） | P3 |

**给使用者的判定指引（同步写入原型提示区）**：

| 你要断言什么 | 用哪种 |
|---|---|
| 按钮上的文字内容 | 断言文本（现有，读控件属性） |
| logo / icon / 图片长得对不对 | 视觉基线对比（P1） |
| 颜色状态对不对（红点/置灰/主题色） | 颜色断言（P1 可选） |
| 以上全都要 | 主断言 + 多条辅助断言一次配齐，一次执行全量出结果 |

## 三、可行性证据（行号级）

1. **截图字节**：`appOperator.get_screenshot`（359-361）只挂 allure 不返回图像；视觉断言直接用 `driver.get_screenshot_as_png()`（`common/appium/popup_handler.py:162` 已有同款「拿字节→挂 allure」用法）。
2. **元素区域裁剪**：`save_element_image`（422-457）已有「整屏截图→裁元素区域→返回路径」完整先例（`get_element_rgb` 逐像素读取同源）；需修复其百分比换算隐含 DPR=1 的隐患（视觉断言裁剪照抄前先校准）。
3. **图像库**：.venv 实装 Pillow 8.4.0 / numpy 1.24.4 / cv2 4.2.0.32 / skimage 0.16.2（SSIM 老版本用 `skimage.measure.compare_ssim`，或直接 cv2 实现）——**零新增依赖**。
4. **Allure 展示**：`web_platform/allure_tweaks.py` 已对报告图片附件做缩略+点击原图；三联图（横向拼接一张 PNG）一次 attach 即可，展示层零改动。
5. **基线存储惯例**：`config/` 存资产进 git、`output/` 存一次性产物（`common/video_evidence/config.py:115-117` 注释明确）。基线图随元素走 → `page_objects/.../elements/baselines/<元素文件名>/<元素名>.png`（约定路径，无需改 `CreateElement.create` 签名）。
6. **失败证据链**：`cases/app_ui/conftest.py:136-219` 失败自动截图+证据视频挂 allure——多断言「每个失败当场截图」与此叠加，业务零侵入。

## 四、风险与对策

| 风险 | 现状证据 | 对策 |
|---|---|---|
| 分辨率/DPR 不一致导致裁剪错位 | `save_element_image` 百分比换算隐含「截图像素=window 逻辑尺寸」；caps 无分辨率字段 | 首版限单设备型号；比对前校验实际图与基线尺寸，不一致报「分辨率不匹配，请重新采集基线」，不硬比 |
| 横竖屏切换 | 全仓无 rotation 处理 | 首版声明仅支持竖屏元素；后续如需再扩展 |
| 基线过期（App 改版） | —— | diff 图人工确认；「更新基线」入口一键重采；基线文件进 git 可追溯版本 |
| 动态内容误报（时间/头像/轮播） | —— | 阈值可调（默认 0.95）；忽略区域列 P2；先靠阈值吸收 |
| 跨分辨率复用 | 两台测试设备分辨率不同 | P2 验证项：等比缩放后比 SSIM |

## 五、多断言（主断言 + 辅助断言）设计要点

- **位置**：定位器「添加测试用例」弹窗 ③操作栏——主断言 = 现有操作类型（语义不变）；主类型为断言类时出现「辅助断言」区，可加 0~N 条。
- **辅助类型集合（P1）**：文本=（现有）/ 存在 / 消失 / 视觉基线 / 颜色。Toast 为页面级断言，不进元素辅助集。
- **执行语义（用户确认）**：**全量执行**——主断言失败不停，辅助断言继续跑；**每个失败当场截图留痕**；全部跑完后若有失败，抛一条 AssertionError 汇总全部失败明细（序号/描述/实际值），逐条结果与三联图全部入 allure 报告。一次执行看全所有断言结果。
- **数据结构**：`step = {type, element, param, aux_asserts: [{type, param, ...}]}`；生成时仍是一个页面方法 `assert_<el>(self)`，方法体内逐段执行。
- **改动面**：8 处（清单见需求文档·开发章节）。

## 六、结论

1. 视觉断言**零新增依赖、有完整先例可抄**，P1（元素基线对比 + 颜色）风险可控，直接命中「logo/icon/切图文案」的断言诉求；
2. 多断言的执行端证据链（失败截图/视频/allure）已全自动，业务侧只需「逐段执行 + 汇总抛错」；
3. 原型与需求文档见同目录 `proto-multi-assert.html` 与 `多断言与视觉断言需求.md`。
