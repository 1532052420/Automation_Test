## 一、需求还原

现有弹窗「保存到哪一步」三个选项：① 仅元素 / ② 元素+用例+操作 / ③ 登记随机弹窗。改法：

1. **② 中增加第 4 栏「断言」**：流程变为 ①元素 → ②用例 → ③操作 → **④断言**；
2. **操作栏的 4 种断言类型（存在/文本/Toast/消失）全部挪到断言栏**——操作栏只留动作类；
3. **断言栏可多选组合**：普通断言（存在/文本/Toast/消失）+ 特殊的**视觉断言**；
4. 四栏太宽 → **底部横向滚动条**。

一句话：把「一步 = 一种操作（断言是操作的一种）」改成「**一步 = 操作 + 断言组合**」——动作与校验解耦，一次录入、一次执行、全量出结果。

## 二、布局与交互设计

- 弹窗宽度 `1240px → 1600px`（`style.css:261`），仍 `max-width:96vw`；`.flow-cols` 由三列改四列（`style.css:278`），`.modal-body` 加 `overflow-x:auto`——**窄屏自动出横滚条，满足"太宽了底部就增加滚动条"**；
- ④断言栏默认停靠可视区右侧；超出视口时顶部出现"→ 断言"引导小箭头。

### 2.2 ③操作栏（瘦身后）

- 保留：点击/输入/长按/坐标点击/截图/固定等待/轮询等待/出现才点击/自定义代码 + 特殊操作（收起键盘/首启弹窗）；
- **移除**：断言存在/断言文本/断言Toast/断言消失（→ ④栏）；
- **新增一个类型「仅断言」**：不执行动作、只跑断言组合（替代原"断言也是一种操作"的纯断言场景，见决策点 A）。

### 2.3 ④断言栏（新）

- **类型多选列表**（checkbox 卡式，勾选即展开参数行）：

| 断言类型 | 参数 | 元素依赖 |
|---|---|---|
| 断言存在 | 等待秒数（默认3） | 需元素 |
| 断言文本 | 期望文本 | 需元素 |
| 断言Toast | toast 文本 | **无**（页面级，行内标注） |
| 断言消失 | 等待秒数（默认2） | 需元素 |
| **视觉断言**（新） | 相似度阈值(默认0.95) + 采集基线按钮 + 基线缩略图 | 需元素 |

- 勾选 ≥1 条时步骤描述自动追加「· 含N断言」；全部不勾 = 纯操作步骤（与现状行为一致）；
- 特殊操作（收起键盘/首启弹窗）选中时断言栏**置灰**（该类步骤无断言语义）；
- 执行语义沿用你已确认的：**全量执行**——逐条断言跑完、失败各自截图（视觉断言附 基线/实际/diff 三联图），最后一条 AssertionError 汇总全部失败明细。

## 三、数据结构与生成代码

### 3.1 步骤数据

```python
step = {
  'type': 'click', 'element': 'webview', 'param': '',     # ③操作
  'asserts': [                                             # ④断言（可空）
    {'type': 'assert_text', 'param': '写新歌'},
    {'type': 'visual_baseline', 'threshold': 0.95},
  ],
}
# 纯断言步骤：type='assert_only' + asserts 非空
```

### 3.2 生成形态（一个页面方法 = 操作段 + 断言段）

```python
def click_webview(self):
    """点击「webview」· 含2断言"""
    self.appOperator.click(self._elements.webview)          # 操作段（原逻辑不变）
    failures = []                                            # 断言段（全量执行）
    self.appOperator.assert_shot_or_record(failures, '文本', 
        self.appOperator.getText(self._elements.webview) == '写新歌')
    self.appOperator.assert_visual_or_record(failures, '视觉基线',
        self._elements.webview, baseline='.../webview.png', threshold=0.95)
    if failures:
        raise AssertionError('%d 项断言未通过：%s' % (len(failures), '；'.join(failures)))

def assert_webview(self):        # 「仅断言」类型 → 纯断言方法（沿用现有命名）
    """断言「webview」：存在 + 文本"""
    ...
```

- 用例行仍是薄调用：`page.click_webview()` / `page.assert_webview()`（断言参数 P1 固化在方法体，所见即所得；参数化列 P2，见决策点 B）；
- 无 `asserts` 字段时生成代码与现状**逐字节一致**（兼容承诺）。

## 六、可行性结论

**可行，无技术阻塞**。三条硬依据：① 布局改动是纯 CSS（grid 列数 + overflow）；② 代码生成器本就逐类型拼方法体，「操作段+断言段循环」是加法改造，执行引擎零改动；③ 视觉断言依赖与先例（裁图/SSIM/三联图/allure）在上轮调研已逐行号论证。主要工作量在前端交互与生成器镜像（#3/#4），属常规改造量。

**风险两条**（均有对策）：
1. **编辑回填**：断言配置固化在页面方法体内，旧步骤重新打开弹窗时需从方法体反解析回填——生成代码规则化、可反解；P1 可先不做回填（重复添加同名方法即覆盖更新，现有 upsert 机制）；
2. **横滚可用性**：第四栏在窄屏可能落在首屏外——用引导箭头 + 断言栏置顶钉住参数区缓解。
