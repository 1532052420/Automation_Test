界面这一层做得比预期扎实：项目管理、元素管理、用例编排、测试用例、测试套件五块面板都跑得通，用例编排的 14 种操作、三栏布局、拖拽排序都可用；后端校验尤其干净——我实测了 10 条非法输入（空名、重名、非法状态、缺元素、元素不在元素库、元素文件不存在、空步骤、坐标格式错、缺参数），全部被正确拦截，且错误信息是人话。用例保存后会真的编译成「页面文件 + 用例文件」并落盘，删除时也会连生成物一起清理，引用它的套件同步解绑——这条链路是通的。

但整条链路里有一处硬断点，和一处系统性的参数错位：

  • 执行链路目前跑不起来。平台用的 .venv（Python 3.8.20）缺少 pojo.httpResponseResult 模块，任何 APP UI 用例在 pytest 收集阶段就 ImportError。也就是说，前面所有编排工作最终都会在「执行」这一步失败，而平台没有任何地方提示"环境缺依赖"。
  • 执行参数放错了地方。conf 文件 / udid / 发起人这三个决定"跑在哪台设备、谁跑的"的参数，唯一入口在「测试套件」面板顶部，却被「用例编排」「测试用例」两个页面的执行按钮隐式复用。用户在编排页点执行，跑的是套件页里选的那台设备，页面上一个字都看不到。

二、阻断级问题（P0）

P0-01 · 执行链路不可用 · 已复现

平台缺依赖模块，任何用例都在收集阶段就崩

现象

平台执行用例时，pytest 进程在收集阶段直接 ImportError，任务必然 FAILED。用户在界面上只能看到任务失败 + 一大段堆栈，看不出是环境问题。

复现 
cd /Users/ouyang/Desktop/AutomationTest
.venv/bin/python -m pytest -c config/pytest.ini --collect-only -q \
    cases/app_ui/android/demoProject/test_orch7.py

# ModuleNotFoundError: No module named 'pojo.httpResponseResult'
#   cases/.../test_orch7.py:5
#   → base/.../app_ui_android_demoProject_client.py:7
#   → common/appium/appOperator.py:11
#   → common/httpclient/doRequest.py:5  <-- 这里

换成任意原生用例（如 test_home_check.py）结果完全相同，说明与编排无关，是环境级的。影响面覆盖全部 APP UI 用例，以及所有 import doRequest 的接口测试链路。

根因

common/httpclient/doRequest.py 第 5 行在模块顶层 from pojo.httpResponseResult import HttpResponseResult，但工作区里 pojo/ 下只有 __init__.py / app_ui_config.py / app_ui/ / app_ui_devices_info.py / elementInfo.py / httpserver_config.py / report_config.py——没有 httpResponseResult.py，也没有 HttpResponseResult 的类定义（全库搜索只命中 doRequest.py 与两份设计方案文档）。git status pojo/ 干净，说明这个文件从未被 git 跟踪，属于框架自带文件在某个环节丢失。而 output/app_ui/xiaomi/ 下 9-12、9-13 的历史产物说明它曾经是能跑的。

为什么这次特别值得修

这不是一个"跑不通"的问题，而是一个"跑不通还看不出来"的问题：平台的设备配置页会检测 adb、检测 Appium、甚至提前检测被测 App 有没有安装，唯独不检测框架本身能不能 import。用户按界面提示逐项排查，永远不会得到正确结论。

建议
  • 补回 pojo/httpResponseResult.py（从历史备份/上游框架包找回，不要凭猜重写）；若短期取不回，把 doRequest 的顶层 import 改为用到时才 import，让 APP UI 链路先解耦。
  • 在平台的 /api/status 或设备配置页增加一次「环境自检」：python -c "import base.app_ui.android.demoProject.app_ui_android_demoProject_client" 冒烟，失败时把结论直接显示在页面顶部（而不是等用户点了执行才炸）。

三、逻辑缺陷（P1）

P1-01 · 执行参数错位 · 已复现

决定"跑在哪台设备"的参数藏在另一个页面里

conf 文件 / udid / 发起人这三个参数，全平台唯一入口是「测试套件」面板顶部的卡片。但 app_testing.js 里 _runBody() 是从 #suiteConf / #suiteUdid / #suiteOwner 读值，然后被四个执行入口共用：

执行入口传 conf传 udid传 包名/Activity传 发起人执行后能看到进度吗
选择用例 → 开始执行页面可见可选页面可见页面可见不传有进度条 + 实时日志
测试用例列表 → 执行取套件页的值取套件页的值不传取套件页的值只有一句 toast
用例编排 → 执行此用例取套件页的值取套件页的值不传取套件页的值只有一句 toast
测试套件 → 执行同页可见同页可见不传同页可见只有一句 toast

实测证据：我以 conf_file: "" 调 POST /app-testing/api/cases/9/run，后端静默回退到 conf 列表第一项，返回：

{"ok":false,"msg":"设备 10AG561473007KL 不在线（当前在线: 无）"}

用户根本没选过设备，却被一个陌生的设备编号告知失败。换成显式指定 kuaige conf，报错立刻变成 2HSYD24521203953——说明 conf 确实生效，只是"用哪一份"这件事完全不可见。

建议

把「设备 / 执行参数」抽成一个共用组件（或统一成"点执行弹确认框，框里带设备与包名"），让四个入口看到的是同一份、且是当前页面可见的那一份；至少在编排页与用例列表页执行前，把"即将在 设备X / App Y 上执行"显式回显一次。

P1-02 · 文案与实现相反 · 已复现

「设备配置」页的覆盖参数，对编排/套件执行完全不生效

「设备配置」面板写着「以上参数仅对本次执行生效」，套件面板的卡片也写着「套件与用例执行共用，与「设备配置」页同一数据源」。实际是：

  • 两处只共享 conf 文件列表，不共享选择状态——在设备配置页选好 kuaige 设备，切到套件页执行，用的仍是套件页自己那份下拉的值。
  • 设备配置页的 appPackage / appActivity 覆盖，只有「选择用例」页的执行会带上；编排页与套件页的执行根本不传这两个字段。

结果就是：一个叫「设备配置」的页面，配置结果对四个执行入口里的三个无效。用户在这里改包名、换设备，然后在编排页执行，配置被静默忽略。

建议

要么让执行参数成为全局单例（一处改、处处生效，且各页面回显当前值），要么删掉"共用"这类承诺文案、把参数收回各自页面。

P1-03 · 模型缺一环

「项目」只是一个标签，跟执行没有任何关系

项目管理页的副标题写着"一个项目管理一组用例与套件"。实际数据模型里，project_id 只用于列表筛选与归属展示，不影响任何执行行为：

  • 用例仍必须手选「元素文件」（kuaigeLoginElements.py），项目不携带元素库。
  • 项目不携带被测 App（包名 / Activity）、不携带默认 conf。
  • 既有用例 #7「登录冒烟·编排」的 project_id 是 null，而项目「快歌App」的用例数是 0、套件数是 0——用户建了项目，但没有任何机制把已有用例归进去，只能逐条编辑用例去改归属。

对使用者来说，"项目"目前唯一的价值是列表上一个筛选器，却承担了"统一归口"的心智预期，落差明显。

建议

让项目承载「被测 App + 默认元素库 + 默认 conf」三件事，编排用例时自动带出；再补一个"把选中用例批量归入项目"的入口。

P1-04 · 硬编码 · 代码走读

编排用例启动的 App 是写死的，界面上改不了

后端 app_testing/routes.py 支持 app_package / app_activity 字段，codegen.compile_case() 也会把它们写进生成用例的 setup_class：

self.appOperator.start_activity('com.recordlife.kuaige', 'com.recordlife.kuaige.feature.main.MainActivity')

但前端编排页没有任何输入框提交这两个字段，于是永远落到 codegen 里的常量：

DEFAULT_APP_PACKAGE  = 'com.recordlife.kuaige'
DEFAULT_APP_ACTIVITY = 'com.recordlife.kuaige.feature.main.MainActivity'

现在因为恰好和当前被测 App 一致，问题被掩盖了；一旦换 App 或换项目，编排生成的用例会去启动一个错误的包，而用户在界面上找不到任何地方可以改。

建议

短期在编排顶栏补两个可选输入（默认值来自所选项目/conf，而不是写死在代码里）；中期按 P1-03 收到项目上。

P1-05 · 数据丢失风险 · 代码走读

切换用例不提示未保存，编排内容会被静默清掉

编排页顶部的用例下拉直接绑定 selectOrchCase()，该函数无条件用新用例的步骤覆盖 _orchSteps：

$('#orchSel').addEventListener('change', () => selectOrchCase($('#orchSel').value));
// selectOrchCase: _orchSteps = c ? (c.steps || []).map(...) : [];

用户在编排画布上拖了 10 个步骤、改了参数，然后手滑切了一下下拉，全部丢失，没有"未保存"提示、没有二次确认。画布上也没有任何"已修改未保存"的标记。同样的问题存在于「新建用例」按钮（selectOrchCase(0) 直接清空画布）。

建议

维护一个 dirty 标记（步骤数组与载入时快照比对），切用例/点新建时若有改动则弹确认；顶栏"保存用例"按钮在有改动时给出视觉提示。

四、体验与一致性问题（P2）

P2-01 · 状态语义错误 · 已复现（截图）

套件「执行状态」与「最近结果」两列打架：NOT_RUN 被显示成 PENDING

表格里同一行并排出现 NOT_RUN（执行状态列）和 PENDING（最近结果列），表达的是同一件事。根因在 suiteResultHtml()：

/* NOT_RUN 复用 PENDING 徽章样式（statusBadge 只认 PENDING/RUNNING/PASSED/FAILED/ERROR） */
const raw = s.execution_result || s.execution_status || 'NOT_RUN';
return statusBadge(raw === 'NOT_RUN' ? 'PENDING' : raw);

把"从未执行"翻译成"PENDING（等待中）"是会误导人的——PENDING 在同一个平台的执行器里是有明确含义的（任务已创建、进程待起）。用户看到 PENDING 会以为"排队中"。

建议

给 statusBadge 补一个 NOT_RUN → 未执行 的独立徽章（灰色），不要复用 PENDING；两列合并成一列「最近结果」，未执行显示「—」。

P2-02 · 无效按钮 · 已复现

空套件的「执行」按钮照常可点，点了才告诉你不行

截图里 5 个套件的用例数都是 0，但「执行」按钮全是可点的蓝色主按钮。实测点击后返回：

{"ok":false,"msg":"该套件未包含任何测试用例"}

同理，设备离线时「开始执行」也是可点的，点了才报"设备不在线"。平台的设备状态（在线/离线）在前端是拿得到的（/api/status 每 10 秒轮询一次，页脚已经在显示），完全可以用来做按钮禁用与原因提示。

建议

用例数为 0 的套件、无在线设备时的执行按钮，统一禁用并把原因写成按钮的 tooltip 或旁边的一行小字。

P2-03 · 前后端约束不一致 · 已复现

套件与用例的项目归属，前端拦了、后端没拦

前端 renderSuiteModal() 明确注释"套件选了项目 → 可选用例只列同项目与未分组（跨项目用例不允许混入）"。但后端 _clean_suite_case_ids() 只校验用例是否存在，不校验项目一致性。实测把一个属于项目 #4 的用例塞进未分组套件，成功：

POST /app-testing/api/suites
{"name":"体验套件2","project_id":"","case_ids":[9]}
→ {"ok":true, ... "case_ids":[9] ...}

前端定下的规则可以被直接绕过，而且绕过之后界面自己也不拦——这条约束实际上不存在。

建议

要么后端补上一致性校验，要么明确"套件允许跨项目"，并删掉前端那句注释与过滤逻辑。二选一，别停在中间。

P2-04 · 缺失功能 · 已复现（截图）

「选择用例」页没有搜索框，但代码里已经为它铺好了路

用例树渲染时专门给每个节点写了 data-key（"文件+类+方法"的小写全文），注释明确写着"供顶部搜索框过滤"——但 run.html 的 #panel-cases 里只有全选/全不选/开始执行三个控件，没有那个搜索框。用例一多（当前 8 个文件，实际项目会更多），用户只能靠肉眼在树里翻。

对比之下，「测试用例」「测试套件」「元素管理」三个面板都有搜索/筛选控件，唯独这个执行入口没有。

建议

补上搜索输入框（按 data-key 过滤，代码已经准备好）；顺带补"按文件折叠/展开"。

P2-05 · 命名体系断裂 · 已复现（截图）

同一条用例，在两个页面是两个名字

在「测试用例」面板里它叫「登录冒烟·编排」，到了「选择用例」面板变成「TestOrch7::test_orch_7」，在文件树里又是 test_orch7.py。三个名字指向同一条用例，用户需要自己建立映射关系。

编排页的「用例信息」栏里显示了元素文件、步骤数、创建人、创建时间，却没有显示这条用例编译后的 pytest 节点——而那正是执行与报告里使用的标识。

建议

在用例树里对编排生成的用例显示中文名（后端 node → 用例名是能反查的），或至少在用例详情/编排页把节点名显示出来，让两端能对上。

P2-06 · 界面冗余 · 已复现（截图）

报告页两张表数据源完全相同；全平台执行记录有四处入口

「最近执行」取 /api/runs 前 10 条，「报告列表」取同一接口的全量分页——两张表的列高度重叠（Run ID / 时间 / 状态 / 目标 / 操作），只是后者多一列"报告是否已生成"。无记录时，两块空态加下面第三块「用例执行记录」的占位，把一屏占满却什么都没说。

同一类信息在平台里散在四处：选择用例页的"执行中"卡、报告页的"最近执行"、报告页的"报告列表"、报告页的"用例执行记录"，加上每个套件还有自己的"执行历史"弹窗。

建议

合并成一张表：Run ID / 时间 / 目标 / 结果 / 报告 / 操作，顶部放统计卡即可；「用例执行记录」保留为选中某条 run 后的下钻区。

P2-07 · 默认值不合理 · 已复现（截图）

首次进入 AppUI 自动化，默认停在「设备配置」

无 hash、无本地记录时 showRunPanel() 落到 'exec'（菜单最后一项），于是新用户打开这个模块，第一眼是一个需要先接设备才能填的页面；而侧边栏第一项「项目管理」在模板里写着 class="on"，与 JS 实际选中的项不一致（JS 会覆盖，所以只是模板里的死属性）。

建议

默认落到「选择用例」或「项目管理」（前者是主流程入口，后者是起点）；同时清掉模板里那个无效的 class="on"。

P2-08 · 前置提示缺失 · 已复现

设备离线只在两个地方说，其余页面照常让你点执行

页脚有一个「设备 离线」的红点，「设备配置」页有一行「未检测到在线设备」的胶囊——这两处做得很好。但「用例编排」「测试用例」「测试套件」三个面板完全没有设备状态提示，执行按钮也不禁用。用户在这三页点执行，得到的是：

{"ok":false,"msg":"设备 10AG561473007KL 不在线（当前在线: 无）"}

顺带一提，这个报错信息本身写得不错（给出了 udid 和在线列表），但它是"事后告知"，不是"事前预防"。

建议

把设备/Appium 状态做成可复用的顶部条（首页与接口测试页也适用），离线时在执行按钮旁给一行说明。
